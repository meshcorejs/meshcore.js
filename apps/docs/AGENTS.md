# @meshcorejs/docs — agent guide

## Purpose

The documentation site (https://meshcorejs.dev): Fumadocs on Next.js, one sidebar tab per package, guides written
by hand and an API reference generated from the TypeScript sources by TypeDoc at every `dev` / `build`. Private
workspace package, exported as a static site (`output: 'export'`) and deployed to GitHub Pages by `docs.yml`.

- Depends on: `next`, `react`, `fumadocs-*`, `typedoc` + `typedoc-plugin-markdown`, **TypeScript 6.0.x pinned here**
  (TypeDoc does not support TypeScript 7; the rest of the repo uses 7). Dev: `@meshcorejs/client` (`workspace:*`)
  so the snippets resolve their imports — never used at runtime.
- Used by: nobody; it is published as a website.

## Layout

```
app/                     Next routes as scaffolded by create-fumadocs-app: (home)/ landing, docs/ layout + [[...slug]], api/search, llms*, og/,
                          sitemap.ts + robots.ts (built from lib/source + siteUrl)
app/(home)/page.tsx      the landing: JSX only (no data constants), composed from components/home.tsx
components/mdx.tsx       MDX components (fumadocs-ui defaults + Steps/Step)
components/home.tsx      landing pieces: Code (ServerCodeBlock), Install (+ copy-button.tsx, client), Badge, Card, SectionTitle, PluginCard, PublishCard, PackageCard
lib/source.ts            defineDocs (fumadocs-mdx macro) + loader({ baseUrl: '/docs' })
lib/shared.ts            appName, siteUrl (NEXT_PUBLIC_URL), docsRoute, gitConfig, githubUrl
lib/plugins.ts           the static plugin directory shown on the landing (name, description, official | community, npm?, repo)
lib/snippet.ts           readSnippet(file, region?) — reads snippets/ at build time; extractRegion() is the pure part (tested)
content/docs/<tab>/      one folder per package = one sidebar tab (meta.json with root: true, explicit pages order)
content/docs/client/     index, getting-started, then one folder per group, each with its meta.json (title, pages):
                          guides/ (task pages, defaultOpen), client/, commands/, events/, jobs/, permissions/, plugins/, replies/
content/docs/plugins/    the Official plugins tab: overview + one page per published plugin (install, configure, on the air, options, replies), no TypeDoc reference
content/docs/<tab>/reference/   GENERATED by scripts/generate-reference.ts, gitignored, never edited
content/drafts/<tab>/    guides written but NOT published (outside the docs collection): protocol, transports, testing
snippets/<tab>/*.ts      code shown in guides, compiled by `typecheck`, included with <include lang="ts">…#region</include>
snippets/client/guides/  the club bot of the nine task guides (/heard, /announce, polls, advert job, a Vitest file)
snippets/plugins/*.ts    the configure() snippets of the official plugins
snippets/home/*.ts       code shown on the landing, same rule, read with readSnippet()
scripts/generate-reference.ts   TypeDoc runner (one package at a time) + post-processing
scripts/reference/       pure helpers: markdown.ts (splitTitle, withFrontmatter, and the ModuleMove / rewriteLinks /
                          remapLink trio that moves TypeDoc's path-named module folders to main/ and mock/ and
                          rewrites the links crossing them), meta.ts (sidebar meta), packages.ts (PACKAGES table)
test/reference.test.ts   unit tests of the pure helpers (run by the root `pnpm test`)
test/snippet.test.ts     unit tests of extractRegion()
next.config.mjs          output: 'export' (static site in out/), images unoptimized; no redirects, no proxy
public/.nojekyll         keeps GitHub Pages from ignoring the _next/ folder
```

## Public API

None (website). Scripts: `pnpm --filter @meshcorejs/docs dev | build | start | reference | typecheck`.
`REFERENCE_STRICT=1 pnpm --filter @meshcorejs/docs reference` forces `notDocumented` on every package (to measure).

## Rules

- Everything is English. Tone of the README: rules are stated as rules with their reason, no apology.
- One tab per package, guides first, then a `---Reference---` separator and the generated `reference/`.
  Every page ends with a `## Reference` section linking the generated pages it covers (task guides call it
  `## Go further` and add the related group pages).
- The client tab has two kinds of pages. A **task guide** (`guides/`) is titled with the task, opens with one
  sentence of context, shows the code first (a snippet of the club bot), then `## What happens` in three to
  five short sentences, then `## Go further`. Thirty to fifty lines. A **group page** (`client/`, `commands/`…)
  explains one thing, its behaviour and its rules, with tables for options and members.
- Prose rules for the client tab: no dash inside a sentence (no `—`, no ` - `), no arrow (`->`, `→`), a
  colon only before a code block or a list. Short sentences. Mesh vocabulary in the guides (DM, channel,
  node), technical but plain in the group pages. Check with
  `grep -rn -e ' — ' -e ' -> ' -e '→' content/docs/client` (must print nothing outside `reference/`).
- Snippets keep a relative include path from their page: a page in a group folder uses
  `../../../../snippets/…`, a page at the tab root `../../../snippets/…`.
- Only the `client` tab has guides for now. `protocol`, `transports` and `testing` publish their overview and the
  reference; their guides live in `content/drafts/<tab>/` until they are finished, and come back by moving them
  to `content/docs/<tab>/` and listing them in `meta.json`. `Contributing` is not a page: the client overview
  links to `CONTRIBUTING.md` on GitHub.
- The Official plugins tab has one page per package under `plugins/*`; its options table mirrors the package
  README and its `DEFAULTS`.
- Folder loading first. Every example is a file with a default export under `commands/`, `events/`, `jobs/`,
  `roles/`, `permissions/` or `plugins/`, loaded by `load: import.meta.dirname` in `main.ts`.
  `client.register()` is shown once, on the Bricks and loading page, as the way to add a brick built in code.
- The landing (`app/(home)/page.tsx`) is written for someone who owns a MeshCore radio: mesh vocabulary (DM,
  channel, node), no framework jargon in the prose; the code speaks for itself. Icons are Lucide through
  `<Icon icon="lucide:…" />` from `@iconify/react` (loaded from the Iconify API in the browser). Plugins shown
  on the landing come from `lib/plugins.ts`.
- Code in guides that is longer than one line lives in `snippets/` and is included by region: a snippet that
  no longer compiles fails `pnpm typecheck`. Short one-liners stay inline.
- TypeDoc's `notExported` and `invalidLink` validations are strict (`app.validate`, checked by hand since
  `treatWarningsAsErrors` only applies to TypeDoc's own CLI) and always fail the build. Whether every top-level
  export needs a doc-comment is a separate, home-made check (`undocumented()` in `scripts/generate-reference.ts`,
  walking classes, interfaces, functions, type aliases, variables and enums — not their methods or properties),
  gated per package by `documented` in `scripts/reference/packages.ts`; it is `true` for all four packages, so
  a top-level export without a doc-comment **fails the docs build**. A comment made only of `@param` tags does
  not count: write a summary line. `REFERENCE_STRICT=1 pnpm --filter @meshcorejs/docs reference` lists the
  missing ones. `@internal` symbols are excluded.
- Keep the scaffold: do not rewrite the Next/Fumadocs plumbing to taste; change `lib/shared.ts`, the content and
  the scripts.
- The generated reference is never committed, never linted (`biome.jsonc`, `_typos.toml`, `knip.json` exclude it).
  `.source/` (fumadocs-mdx output) is ignored the same way (`.gitignore`, `biome.jsonc`, `knip.json`).
- `knip.json`'s `apps/*` entry ignores the `tailwindcss` dependency: it is only consumed through a CSS `@import`,
  invisible to knip's import graph.

## Testing

- `pnpm vitest run apps/docs` — the pure helpers. The real test of the site is
  `pnpm --filter @meshcorejs/docs build` (TypeDoc strict + `next build` + static export to `out/`), run by
  `docs.yml` on every PR and push, then deployed to GitHub Pages from `main`.
- Local preview: `pnpm --filter @meshcorejs/docs dev`, then http://localhost:3000.

- Static export rules: every route handler (`api/search`, `llms*`, `og/`, `sitemap.ts`, `robots.ts`) exports
  `dynamic = 'force-static'` and dynamic segments have `generateStaticParams`; the search dialog runs in the
  browser on the index written at `/api/search` (`RootProvider search={{ options: { type: 'static' } }}`,
  `staticGET`); `/docs` is a page with a `<meta http-equiv="refresh">` to `/docs/client` because a static site
  cannot redirect; `.md` content negotiation is gone, `MarkdownCopyButton` points at the static
  `/llms.mdx/docs/…/content.md`. `NEXT_PUBLIC_URL` (set in `docs.yml`) is `metadataBase` and the sitemap base;
  it includes the `basePath`, so URLs are built by concatenation (`${siteUrl}${page.url}`), never with `new URL()`,
  which would drop it.
- SEO: all site-wide metadata (description, keywords, robots, canonical `./`, Open Graph, Twitter card) lives in
  `app/layout.tsx`; docs pages override title, description and image in `generateMetadata`. Share images are
  explicit `.png` routes (`og/image.png` for the landing, `og/docs/[...slug]` for pages) rather than the
  `opengraph-image.tsx` convention, whose export has no extension and no content type on GitHub Pages.
- Local preview of the export: `pnpm --filter @meshcorejs/docs serve` (Python `http.server` on `out/`; it does
  not resolve extensionless URLs the way GitHub Pages does, open `/docs/client.html` directly).
- The export weighs about 220 MB (343 pages, each shipping the full sidebar tree in its RSC payload). Under
  the GitHub Pages limits, but worth shrinking if the reference grows.
