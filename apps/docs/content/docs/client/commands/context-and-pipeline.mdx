## The context

The handler receives a `CommandContext`.

| Member                      | Role                                                                    |
| --------------------------- | ----------------------------------------------------------------------- |
| `ctx.message`               | The triggering `Message`.                                               |
| `ctx.author`                | Its author.                                                             |
| `ctx.args`                  | The parsed arguments, typed from the builder.                           |
| `ctx.reply(content)`        | Answers where the command was triggered. Takes a string or a `MessageBuilder`. |
| `ctx.replyDM(content)`      | Answers in a DM. Rejects when a channel author cannot be verified.      |
| `ctx.can(permission)`       | Whether the author holds a permission.                                  |
| `ctx.canManageRole(role)`   | Whether the author ranks above that role.                               |
| `ctx.canManageContact(c)`   | Whether the author ranks above that contact.                            |

## The pipeline

Every message that matches the trigger rule goes through these steps in order.

1. Trigger. Does it match a registered name or alias?
2. Max hops. Is the message within `client.maxHops`, if one is set?
3. Scope. Is the command allowed in this DM or channel?
4. Age. Is a backlog message too old?
5. Permissions. Does the author hold every required permission?
6. Cooldown. Did the author run this command too recently?
7. Arguments. Do the values match the declaration?
8. Handler.

Every refusal emits `commandDenied` with a typed `DenyReason`. A message from beyond `maxHops` is denied
silently with `{ type: 'tooFar', hopCount }`, before the helper branch runs — so an out-of-range `@Bot` gets
nothing either. On a channel every refusal is silent — the bot only speaks to answer a command it actually
ran. In a DM the others answer with a text from `client.replies`.

## When the handler throws

The client emits `commandError` and answers with `client.replies.internalError`. The error's detail never
goes on the air. `setErrorHandler()` replaces that reply for one command.
